Two constraints

Faster than 4 ms. Far fewer false alerts.

Before is the plan as submitted: one ±step per site, and a log reopened for every record. After is the tuned sensor: each check weighted by its own evidence, each site capped, and the log kept open.

Detection runtime under 4 ms.

Measured in the C++ sensor on —: 2,000 runs over the 8 handshakes of the attack capture, where every site writes a log record. Each run includes parsing, fingerprints, checks, the score step and the hash-chained log write.

What changed: the hash-chained log used to open and close its file for every record, which cost up to 2.2 ms on an alert. It now stays open and still flushes every record, so a crash loses nothing that was written before. Live in this deployment: the JavaScript port of the engine decides in — at p99 inside a Vercel function.

Fewer false alerts.

Monte Carlo of whole tests, both methods on the same random sites. A false alert is a test without an interceptor that ends in an alert. Thresholds stay at ±4.60 (α = 0.01, β = 0.99) for both.

What changed in the math.

The paper's walk adds one fixed step per site. The tuned walk asks each check separately how much more likely its result is with an interceptor, adds those log-likelihood ratios, and caps the sum for each site.

Before

Jung et al. 2004, one Bernoulli trial per site

any check failed:  step = ln((1−θ₁)/(1−θ₀)) = ln(0.8/0.1) = +2.08
otherwise:         step = ln(θ₁/θ₀)        = ln(0.2/0.9) = −1.50

A renewed certificate counts as much as a forged one. Three normal changes in a row raise an alert.

After

Weighted per check, capped per site

step = clip( Σ over checks k of
         failed: ln(p₁ₖ/p₀ₖ)   held: ln((1−p₁ₖ)/(1−p₀ₖ)) ,
       ±4.60/2.5 = ±1.84 )
A: p₀ 0.06 p₁ 0.95   B: p₀ 0.04 p₁ 0.98   D: p₀ 0.06 p₁ 0.90

A benign change usually fails one check while the others still hold, so the site's sum goes down. The cap means at least 3 sites are needed for any decision, so one odd site can never alert alone.
